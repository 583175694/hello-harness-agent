## 实测基线（2026-11-20）

用于判断 #1 的真实收益，避免继续用估算。测试点：生产服务器 `175.178.23.83` 与本机对照。

| 目标                           | 生产服务器      | 本机        | 备注                    |
| ------------------------------ | --------------- | ----------- | ----------------------- |
| `push2.eastmoney.com`          | 0.15s / 200     | 0.18s / 200 | 本轮日志主力目标        |
| `push2ex.eastmoney.com`        | 0.18s / 200     | 0.46s / 200 | 返回 `application/json` |
| `news.qq.com/rain/...`         | 0.06s / 501     | 0.08s / 501 | WAF 拒裸 HTTP 客户端    |
| `api.github.com`               | 1.26s / 200     | 0.61s / 200 |                         |
| `en.wikipedia.org`             | 12s 超时 / 000  | 2.35s / 200 | 服务器不可达            |
| `www.google.com`、`medium.com` | 6.2s 失败 / 000 | —           | 服务器不可达            |

三个由此得出的事实：

- 本轮 Run 的 12 个 URL 全部是境内接口，服务器往返 0.15–0.45s；第三方抓取 75.9s 的开销来自其自身渲染链路，不是网络距离。
- `push2*` 返回 `application/json`，而当前白名单只接受 `text/html`、`xhtml`、`text/plain`（`web-fetch.constants.ts:33`，判断在 `crawlee-web-content.fetcher.ts:157`），开启后仍会被拒。JSON 直通是实际生效的前置条件。
- 服务器到境外站点确实不通（wikipedia 12s、google/medium 6s）。这是「卡住」的真实来源，也是外部通路唯一不可替代的价值。

## 已落地：MCP 暴露审计

`#2` 的第一步只加观测，不改选择逻辑。

- `apps/api/src/tools/tool-exposure/tool-exposure-audit.ts`：Run 级统计器，只累计事实
- `apps/api/test/unit/tools/tool-exposure-audit.spec.ts`：4 个测试
- `agent-runtime.service.ts`：创建审计器、在工具批次与 `tool_search` 完成时记录、Run 结束输出一行汇总

Run 收尾新增日志：

```
MCP 暴露审计 | 直通=32 个 使用=3 个(≈9%) | 延迟=296 个
| tool_search=1 次 平均命中=8.0 fallback=0 次
| 激活=8 个 其中被调用=1 个(≈13%) | MCP调用=4 个
| 直通未用=...,... 等 24 个
```

三个关键数：

- **直通区利用率**：长期低于 20% 说明 32 个名额大幅浪费
- **tool_search 命中质量**：平均命中低、fallback 多说明 BM25 对中文查询不灵
- **激活后是否真被调用**：激活多而调用少，说明检索精度不足，白花一轮模型往返

## 已知的 #2 成因（待改判据）

- 直通名额按 `serverName` 字母序分配（`tool-exposure.service.ts:20`），`Tinyfish` 字母序靠前，独占 32 个名额，`tushareMcp` 的 285 个工具全被挤进 deferred。
- 本次 Run 共 328 个 MCP 工具（Tinyfish 43、tushareMcp 285），全量定义估算 110343 token，因此 cap 不能简单调大。
- 结论：cap 保持 32，改的是入选规则（白名单 → 热度 → 任务相关性），而不是数量。
- 跨 Run 的累计趋势需要落库或日志采集，当前统计仅限单 Run 进程内。

## 修复方案：#1 网页读取分流

**核心原则：能力属于产品，传输属于部署。**

`web_fetch` 是产品能力，必须在所有部署中都可用；「用什么通路拿到字节」是部署事实，随租户、网络环境、是否安装某个 MCP 而变化。因此：

- 不在 Prompt 中写任何优先级或降级顺序
- 不硬编码任何第三方 MCP 的服务器名、工具名
- 不假设某个 MCP 一定存在；不存在时，`web_fetch` 就是单纯的一次直连

**已确认的四项决策**

| 项                 | 决定                                           |
| ------------------ | ---------------------------------------------- |
| `web_fetch` 可见性 | 打开（`tool-availability.ts:7` 改为 `true`）   |
| 第一期范围         | 只做 HTML，JSON 直通留到下一期                 |
| 外部 MCP 抓取工具  | 保留但不在提示词中引导；是否存在完全由部署决定 |
| 直连超时           | 6s                                             |

**分层**

| 层     | 归属 | 内容                                                                                     |
| ------ | ---- | ---------------------------------------------------------------------------------------- |
| Prompt | 产品 | 只描述能力：「需要读取公开网页原文时使用 `web_fetch`」。不出现第三方 MCP，不出现先后顺序 |
| 工具面 | 产品 | 模型只看到 `web_fetch`；降级对模型完全不可见                                             |
| 传输   | 部署 | 直连失败后是否借用外部通路，由该租户的运行时配置决定                                     |

**执行流程**（降级为可选分支）

```
web_fetch(urls, query)
  ├─ URL guard（并发，DNS 加 2s 硬超时）
  ├─ 查 LRU 缓存 ──命中──> 直接出 passage
  ├─ 直连（并发，单 URL 6s）
  │    ├─ 成功 ──> normalizer / ranker / budgeter
  │    └─ 失败 ──> 可升级错误 且 已配置外部通路？
  │                   ├─ 是 ──> 外部通路批量兜底
  │                   └─ 否 ──> 该项终态失败
  └─ 全部成功或已终态失败 ──> 返回
```

关键点：**没有配置外部通路时，整棵树退化成「guard → 缓存 → 直连 → 返回」**，不存在任何隐式依赖。日志和错误文案里也不应出现具体供应商名称。

**升级判据**：只有「换一条出网路径可能成功」才升级。

| 直连结果                            | 升级 | 理由                   |
| ----------------------------------- | ---- | ---------------------- |
| DNS 失败、连接超时、SYN 黑洞        | 是   | 换出口可能可解析       |
| 5xx、429                            | 是   | 对方限流，换 IP 有效   |
| 需要 JS 渲染                        | 是   | 外部通路可能跑真浏览器 |
| 登录墙、验证码、403                 | 是   | UA 与风控差异          |
| 404 等语义错误                      | 否   | 换路径无意义           |
| 内容为空、与 query 不相关、解析失败 | 否   | 问题在内容不在传输     |

**绑定方式**

- 配置项 `WEB_FETCH_FALLBACK_MCP`（形如 `server:tool`），按租户配置，默认空
- 解析来源是该 Run 的 MCP snapshot：配置了但该 server 未连接，视为未配置，直接失败，不重试、不降级到别的 server
- 调用经 `McpConnectionManager` 内部发起，继承外层取消信号，不触发二次审批，禁止递归回落到自身
- 允许存在多条候选通路时按配置顺序尝试，但**顺序只存在于部署配置，不写进 Prompt**

**明确不做的三件事**

1. **不在 Prompt 里写「优先 web_fetch」**。当前 `chat.constants.ts:6-8` 这种句式要删掉，它同时犯了两个错：既暗示了优先顺序，又假定了一个固定工具面。
2. **不在产品逻辑里引用具体供应商**。代码与文案中不应出现 `tinyfish`，该字符串只允许作为配置值存在。
3. **不把「有降级」当成能力前提**。所有 `web_fetch` 的测试与验收必须在「未配置任何外部通路」的条件下通过。

**配套改动**

- 提示词：把 `chat.constants.ts:6-8` 收敛为一句能力描述，不出现第三方名称、不出现优先/降级语义。
- 超时：`web-fetch.constants.ts` 的 `transportTimeoutMs` 由 20s 改为 6s；外层 `toolTimeoutMs` 保持 45s。
- 负缓存：同域名连续 2 次网络层失败后标记不可达 10 分钟；仅在配置了外部通路时才有意义。
- 观测：每个 URL 结果增加 `transport: 'cache' | 'direct' | 'external'`。

**为什么优先级不进 Prompt**

「直连快还是中转快」取决于部署网络，不是产品事实。同一份 URL 集合，我们在内地服务器测得直连 0.15–0.45s、境外站点 12s 超时；换到别的机房结论会反过来。把它写进 Prompt 等于把一个会变的测量结果固化成模型行为。

正确做法：路由在服务端按实测信号做，Prompt 只声明能力。哪个通路更快，用 `transport` 埋点统计出来，而不是断言。

**不改的部分**

`web-fetch/` 下的 extractor、normalizer、quality gate、chunker、ranker、budgeter、LRU 全部保留。外部通路返回的整页原文也必须过这套管线，才能从 37KB 收敛到与 query 相关的 24k 段落。

**不在本期**

- `application/json` 直通（本次日志 12 个 URL 均为 JSON，需另开一期处理）
- 批内并发调度（#5）
- 其余 #2–#9
